# SADD：不背公式 App 软件架构设计文档 v5.1

> 版本：v5.1　修订日期：2026-10-19　适用分支：`main`  
> 本目录是现行架构基线。v5 以 v2.1 为基础，吸收 v4 评审意见，并按“小模块 vibe coding”重构为模块卡。v3、v4 是归档版本（标签 `archive/sadd-v3`、`archive/sadd-v4.0`），不是现行基线。

## 1. 总览

“不背公式”是一款面向高中与大学公共课的公式背诵 App，覆盖 Android 与 Windows 两端，预留鸿蒙接口。产品以“不背单词”App 为原型，只做到功能近似，不使用其代码、账号、品牌或素材。

架构要点：

1. **Rust 核心 + Flutter 共享 UI**：公式解析、量纲、计算、排版、判分、排程、资源包、加密、同步合并与识别后处理都放在 Rust 核心，两端结果一致；Flutter 只负责界面；平台代码只实现少量端口（相册、相机、密钥、通知等）。
2. **单一 C ABI 绑定面**：Dart 经 `dart:ffi` 调用 `fmlcore` 的 C ABI，鸿蒙将来复用同一头文件。
3. **本地优先**：必须先选择游客或注册才能使用；游客数据只在本机加密保存，不向云端提交内容；注册后可开启端到端加密同步。
4. **识别可插拔**：墨迹与照片走同一识别契约；首版交付云端 LLM 识别（仅注册用户、逐次授权）；本地轻量模型是可下载资源包；YOLO 只在实验分支预研。
5. **资源与程序剥离**：内容、字体、模型都是签名资源包；安装包只内置 bootstrap-pack。
6. **识别历史可回收**：保留最近 0–100 次识别，默认 5 次，两阶段垃圾回收。
7. **按模块卡实施**：76 张模块卡（公共核心 52、Android 11、Windows 13；AND-10、WIN-11 已在 v5.1 撤销，编号不复用），每张卡都可以单独交给 AI 编码助手完成。

## 2. 需求基线与文档效力

### 2.1 甲方原始需求（原文）

> 我需要设计一个双平台的轻量化软件，Windows平台和安卓，需要预留鸿蒙的接口。软件的目标是强化背诵能力，以不背单词这款app为原型。新增识别手写公式的功能，预留接入轻量化识别模型或者LLM识别手写公式的能力。加入公式编辑器功能，要求除了ISO标准的字符能正常输入以外，还可以输入LaTeX的公式。公式编辑器以外还要能有公式库功能，可以查看已经录入的公式，还可以在查看公式的时候输入变量充当计算器功能。每个公式都要严格匹配量纲，在录入的时候可以调整量纲，也可以后期自定义。量纲匹配的时候可以把公式代入到别的公式中同量纲的部分作为变量。加入大学公共课内容，包括：高等数学（以同济课本范围到考研数学全部范围计算），大学物理。
>
> 增加一些需求：
> 1.需要很强的可维护性，重读和bug排除要足够方便，注释完整可靠
> 2.搜寻开源的公式库，尝试从开源公式库中获取资源
> 3.可能需要接入YOLO等类似的轻量化识别模型进行手写识别，请准备一个预备方案，不需要写入主分支
> 4.版本控制需要简洁可靠
> 5.用户不登录无法使用软件，如果不注册可以使用游客账户，游客账户为临时账户，不向云端提交内容，本地储存用户数据，转为注册账户后可以同步
>
> 将静态资源剥离出来作为资源包，端侧程序只需要加载通用资源包即可。新增一个功能，合并到手写识别中去，识别相片中的手写公式，而不是仅仅依靠墨迹输入，增加相应的去噪和图像增强算法部分。
>
> 注意设计垃圾回收方案，在识别结束后做一定最近识别的保留，用户可以设置其范围从0到100次，默认保留最近五次的识别，保留内容为上传的图片和识别结果。桌面端和安卓端的输入都要能使用文件管理器进行照片选择。
>
> 请帮我基于这些功能设计一个软件的架构方案，要求架构设计，成熟完整可靠，没有重大安全性问题，性能开销低。

## 3. V1 范围

### 3.1 必须交付

- Android 与 Windows 两端（R01、R41），鸿蒙只预留 C ABI 接口并做编译冒烟（R02）。
- 强制账户入口：游客（本地一等账户，不上云）或注册账户（R24–R26）。
- 注册账户：游客数据可升级接管，可选端到端加密同步（R28）。
- 公式编辑器：ISO/Unicode 字符、LaTeX、结构化编辑、错误定位（R08–R10）。
- 公式库：查看、检索、修订历史、变量赋值计算、单位换算、计算链（R11、R12）。
- 量纲系统：SI 与常用导出量纲、用户自定义单位、严格校验、同量纲代入与防误代（R13–R17）。
- 背诵闭环：书与计划、分组学习、客观判定、组后默写、FSRS 排程、统计与本地提醒（R04、R04.a–R04.j）。
- 内容包：高中数学、高中物理、高等数学（同济版教材范围到考研数学全部范围，按数一/数二/数三区分）、大学物理，分批交付（R05、R39）。
- 手写墨迹识别与照片识别：统一候选、校正、入库流程，去噪与图像增强（R06、R31、R32）。
- 云端 LLM 识别：首版实现，注册用户逐次授权，游客不可用（R07、R40）。
- 文件管理器选图：Android SAF 与 Photo Picker，Windows 文件对话框、拖拽、剪贴板（R37、R38）。
- 识别历史保留与垃圾回收：0–100 次，默认 5 次，保留图片与识别结果（R33–R36）。
- 签名资源包与 bootstrap-pack（R29、R30），开源资源调查与许可登记（R21）。
- 可维护性、排错、注释与版本控制门禁（R18–R20、R22、R23）。

### 3.2 不在 V1 范围

| 项目 | 原因 | 处理 |
| --- | --- | --- |
| 鸿蒙端实现 | 原始需求只要求预留接口 | CORE-44 保留 C ABI 与编译冒烟 |

| 组队打卡与社交 | 功能近似条款明确不做 | — |

## 8. vibe coding 使用说明

### 8.1 一次会话交给 AI 的材料

1. 目标模块卡全文（从 `### CORE-xx` / `### AND-xx` / `### WIN-xx` 标题到下一张卡标题之前）。
2. 该卡依赖的全部模块卡（含间接依赖，即依赖的传递闭包）的 **接口契约** 段（不必附实现约束与验收标准）。
3. 固定附上 CORE-01（目录与工程约定、全局性能预算）与 CORE-02（错误码注册表）的接口契约段。
4. 若卡片引用“README §6 Qx”，附上 §6 对应行。

不需要附其他文档。平台卡已内联它调用的公共签名；若发现内联签名与 01 不一致，以 01 为准。

### 8.3 实施顺序

按 01 §2 的阶段 S0～S7 推进：S0 先搭最小可运行骨架（两端都能启动、加载 `fmlcore` 并调用 `fml_abi_version`），之后每个阶段只增加功能模块。同一阶段内没有依赖关系的卡可以并行，在不同分支上各开一个会话。

S0 首批会话按以下顺序进行，前一步合入 main 后再开下一步：

1. CORE-01（仓库目录、工程约定、工具链锁定文件、全局性能预算）。
2. CORE-02（错误码注册表与生成器）。
3. CORE-03、CORE-04、CORE-41（C ABI 与 Dart 绑定、平台端口契约与组装层、CI 门禁；三者可并行）。
4. AND-01、WIN-01（两端工程与入口；可并行）。完成后两端空壳应用都能启动并显示 ABI 版本，即 S0 出口。

### 8.4 规则

- 模块编号全局唯一，之后不重排；撤销的卡删除正文，在所在文档 §3 模块索引下注明撤销原因与去向，编号不复用。
- 一张卡的改动应集中在它“规模”中列出的目录，约 500 行以内；超出时先拆卡再编码（拆出的卡取下一个空号，同步修订 01 §1～§3）。
- 修改公共契约必须先修订 01 中对应的卡，并检查所有引用它的平台卡；涉及决策的改动在附录 A 新增或修订 ADR。
- 需求与验收的对应关系以 §5 为准；新增验收标准必须标注需求编号。

### 8.5 就绪定义

一张模块卡满足以下各项才算“就绪”，可以交给编码助手（逐卡结论见附录 D）：

- a. 结构：目标、范围、依赖、接口契约、实现约束、验收标准、规模七个字段齐全；规模约 500 行以内，并且只落在一个构建单元（一个 Cargo crate、`app/` Flutter 工程、`server/` 或一个 `tools/<名称>/`）。确需附带少量其他位置的改动（如 `contracts/` 条目、跨语言边界另一侧、归属表的迁移或 CI 配置）时，规模中写明“主包”与“附属”各自的行数。
- b. 依赖闭合：依赖字段与所在文档 §1 依赖图、§3 模块索引一致；CORE 卡只依赖编号更小的 CORE 卡，平台卡只依赖 CORE 卡或本平台编号更小的卡；本卡用到的类型、函数、表与错误码都能在本卡或依赖卡（含间接依赖）的接口契约段找到。
- c. 契约唯一：公共契约只在 01 中定义；02、03 内联的签名与 01 逐字一致。
- d. 契约可编码：函数签名有参数与返回类型；DTO 有字段名、类型、取值范围、是否必填与默认值；错误码有编号、级别、是否可重试与触发条件；表结构有列、类型、约束与索引；文件格式与服务端 API 有版本号、示例与错误响应。
- e. 验收可测：每条验收标准有输入、期望输出或阈值、测量方法，并标注需求编号；性能项引用 CORE-01 全局资源预算表的行名，不另写数字。
- f. 追踪一致：§5“验收所在模块卡”一列与各卡验收标准中的 [Rxx] 双向一致；每条需求至少对应一张卡。
- g. 外部前提：工具链版本、第三方库、账号、证书、供应商与数据许可写在“实现约束”的“外部前提”条目中；未定的引用对应 ADR 或 §6 待确认事项。
