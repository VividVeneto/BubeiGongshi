## 1. 总览

“不背公式”是一款面向高中与大学公共课的公式背诵 App，覆盖 Android 与 Windows 两端，预留鸿蒙接口。产品以“不背单词”App 为原型，只做到功能近似，不使用其代码、账号、品牌或素材。

架构要点：

1. **Rust 核心 + Flutter 共享 UI**：公式解析、量纲、计算、排版、判分、排程、资源包、加密、同步合并与识别后处理都放在 Rust 核心，两端结果一致；Flutter 只负责界面；平台代码只实现少量端口（相册、相机、密钥、通知等）。
2. **单一 C ABI 绑定面**：Dart 经 `dart:ffi` 调用 `fmlcore` 的 C ABI，鸿蒙将来复用同一头文件。
3. **本地优先**：必须先选择游客或注册才能使用；游客数据只在本机加密保存，不向云端提交内容；注册后可开启端到端加密同步。
4. **识别可插拔**：墨迹与照片走同一识别契约；首版交付云端 LLM 识别（仅注册用户、逐次授权）；本地轻量模型是可下载资源包；YOLO 只在实验分支预研。
5. **资源与程序剥离**：内容、字体、模型都是签名资源包；安装包内置CORE-56的最小引擎数据与bootstrap-pack，其余按需下载。
6. **识别历史可回收**：保留最近 0–100 次识别，默认 5 次，两阶段垃圾回收。
7. **按模块卡实施**：96 张模块卡（公共核心 68、Android 13、Windows 15；AND-10、WIN-11 已在 v5.1 撤销，编号不复用），通过README §8.5与附录D §D.10就绪复核后按卡交给AI编码助手完成。

## 2. 需求基线与文档效力

### 2.1 甲方原始需求（原文）

> 我需要设计一个双平台的轻量化软件，Windows平台和安卓，需要预留鸿蒙的接口。软件的目标是强化背诵能力，以不背单词这款app为原型。新增识别手写公式的功能，预留接入轻量化识别模型或者LLM识别手写公式的能力。加入公式编辑器功能，要求除了ISO标准的字符能正常输入以外，还可以输入LaTeX的公式。公式编辑器以外还要能有公式库功能，可以查看已经录入的公式，还可以在查看公式的时候输入变量充当计算器功能。每个公式都要严格匹配量纲，在录入的时候可以调整量纲，也可以后期自定义。量纲匹配的时候可以把公式代入到别的公式中同量纲的部分作为变量。加入大学公共课内容，包括：高等数学（以同济课本范围到考研数学全部范围计算），大学物理。
>
> 增加一些需求：
> 1.需要很强的可维护性，重读和bug排除要足够方便，注释完整可靠
> 2.搜寻开源的公式库，尝试从开源公式库中获取资源
> 3.可能需要接入YOLO等类似的轻量化识别模型进行手写识别，请准备一个预备方案，不需要写入主分支
> 4.版本控制需要简洁可靠
> 5.用户不登录无法使用软件，如果不注册可以使用游客账户，游客账户为临时账户，不向云端提交内容，本地储存用户数据，转为注册账户后可以同步
>
> 将静态资源剥离出来作为资源包，端侧程序只需要加载通用资源包即可。新增一个功能，合并到手写识别中去，识别相片中的手写公式，而不是仅仅依靠墨迹输入，增加相应的去噪和图像增强算法部分。
>
> 注意设计垃圾回收方案，在识别结束后做一定最近识别的保留，用户可以设置其范围从0到100次，默认保留最近五次的识别，保留内容为上传的图片和识别结果。桌面端和安卓端的输入都要能使用文件管理器进行照片选择。
>
> 请帮我基于这些功能设计一个软件的架构方案，要求架构设计，成熟完整可靠，没有重大安全性问题，性能开销低。

## 3. V1 范围

### 3.1 必须交付

- Android 与 Windows 两端（R01、R41），鸿蒙只预留 C ABI 接口并做编译冒烟（R02）。
- 强制账户入口：游客（本地一等账户，不上云）或注册账户（R24–R26）。
- 注册账户：游客数据可升级接管，可选端到端加密同步（R28）。
- 公式编辑器：ISO/Unicode 字符、LaTeX、结构化编辑、错误定位（R08–R10）。
- 公式库：查看、检索、修订历史、变量赋值计算、单位换算、计算链（R11、R12）。
- 量纲系统：SI 与常用导出量纲、用户自定义单位、严格校验、同量纲代入与防误代（R13–R17）。
- 背诵闭环：书与计划、分组学习、客观判定、组后默写、FSRS 排程、统计与本地提醒（R04、R04.a–R04.j）。
- 内容包：高中数学、高中物理、高等数学（同济版教材范围到考研数学全部范围，按数一/数二/数三区分）、大学物理，分批交付（R05、R39）。
- 手写墨迹识别与照片识别：统一候选、校正、入库流程，去噪与图像增强（R06、R31、R32）。
- 云端 LLM 识别：首版实现，注册用户逐次授权，游客不可用（R07、R40）。
- 文件管理器选图：Android SAF 与 Photo Picker，Windows 文件对话框、拖拽、剪贴板（R37、R38）。
- 识别历史保留与垃圾回收：0–100 次，默认 5 次，保留图片与识别结果（R33–R36）。
- 签名资源包与 bootstrap-pack（R29、R30），开源资源调查与许可登记（R21）。
- 可维护性、排错、注释与版本控制门禁（R18–R20、R22、R23）。
- 界面设计方案（v5.2 新增，R42、R42.a–R42.f）：统一的设计系统与可选主题色（两端），按窗口尺寸与输入方式自适应；Android 手机与平板均支持横屏和竖屏，Windows 按桌面键鼠优化（CORE-55、AND-13、WIN-15）。

## 8. vibe coding 使用说明

验证责任：自动项由原卡实现者提交测试；真机项统一由AND-12/WIN-13在S7收集原卡checklist、设备/构建/驱动证据并签字，早期卡的Fake通过不等于真机通过；人工视觉原创性由设计负责人与甲方评审签字；M-CONTENT/M-MODEL由附录C负责人交付。没有证据保持pending，CORE-41按环境矩阵展示，不能从未运行推导通过。

### 8.1 一次会话交给 AI 的材料

1. 目标卡全文。
2. 直接依赖及CORE-01/02的完整接口契约；间接依赖按第6项符号固定点保守选择完整定义块，以生成来源清单为准；不省略选中定义，全部分段读完。
3. 正文提及但闭包外的卡，只附所引用的相关契约段及上下文；说明性下游引用标“（下游说明，非契约）”，无需整卡引入。真正编译依赖必须写入依赖字段，不能以只读材料替代。
4. 本卡 [Rxx] 对应的 §5 全行；§6“影响模块卡”含本卡的全行，及正文引用的 Q 行；引用的 ADR 全行与其补充章节。
5. 本卡将修改的 contracts/ 现有文件、版本锁定文件与已有实现，缺失时明确标未创建。材料附字符数；超过 80000 字符提示拆卡/分段阅读，不可静默省略契约。
6. 材料生成入口为 CORE-57：`node tools/sadd/pack.mjs <卡号> --file <将修改的已有实现>`（可重复 --file）。报告列出裁剪前后字符数、保留符号、闭包外引用与未创建文件；本卡、直接依赖、CORE-01/02 不裁剪，间接依赖按符号固定点保守保留完整定义块。总量超 80000 时输出无损分段，附录 D 登记总量/分段数；编码前必须读完所有分段。报告中的未定义符号 warning 由复核人核实 SDK/第三方/本地来源，不能以启发式结果代替语义复核。新增需要的符号或已有实现文件时重新生成材料，不得静默省略。

平台内联签名若与 01 不一致，以 01 为准并修订平台；下游说明不构成反向编译依赖。如需核对直接消费方的调用片段，可用--file额外附上；反向依赖不是默认材料来源，也不能替代公共契约。§8.6 只决定工具链，材料仍按本节收集。

### 8.4 规则

- 模块编号全局唯一，之后不重排；撤销的卡删除正文，在所在文档 §3 模块索引下注明撤销原因与去向，编号不复用。
- 一张卡的改动应集中在它“规模”中列出的目录，约 500 行以内；超出时先拆卡再编码（拆出的卡取下一个空号，同步修订 01 §1～§3）。
- 修改公共契约必须先修订 01 中对应的卡，并检查所有引用它的平台卡；涉及决策的改动在附录 A 新增或修订 ADR。
- 需求与验收的对应关系以 §5 为准；新增验收标准必须标注需求编号。

契约变更回流（负责人为对应CORE契约卡维护者，文档lead协调消费者）：
1. 编码会话停止依赖接口改动，留下变更单（目标卡/符号、旧/新签名、原因、影响的调用方、兼容/迁移风险、所需验收）。允许继续不依赖此变更的工作。
2. 文档负责人先以`docs(core-xx)`修订唯一所有者01卡；涉及架构先同步ADR，产品取舍登记§6待确认与暂行默认。检查全部引用的平台摘录、目录、op/错误表、阶段与追踪，不在消费卡私造替代契约。
3. 按符号和反向依赖定位所有已合入及在途消费者，列出迁移/重生成清单。先合公共定义，再在各自卡提交中更新调用方；破坏性变化在全体消费者通过前不得合入main。
4. 重新运行SADD检查、生成受影响卡完整材料及字符数；D.10受影响卡回到待复核，在D.12记录受影响条目的消费方确认和复检。已合入实现还需相应构建/契约测试，不以文档检查替代。
5. 变更单由文档负责人登记closed及提交/材料/复检证据后，原编码会话读取新材料继续。

共享写入点（并行会话开始前由lead在卡任务中分配）：`contracts/errors/registry.yaml`与ownership由CORE-02维护者单写，业务卡提交独立变更片段；安装点实现各归自己的install.dart，composition聚合顺序由CORE-36/平台工程卡维护者单写；各文档§1～3、README追踪、ADR与D由文档lead单写。其他分支不顺手重排聚合文件，合并前按契约变更单收敛，不以冲突标记解决语义冲突。

### 8.5 就绪定义

一张模块卡满足以下 a～g 各项并按 §8.5.1 完成整卡语义复核才算“就绪”；附录D §D.10为当前状态，历史“已修订”和机械0项不代表可开工。C卡先修订，未复核卡先复核：

- a. 结构：目标、范围、依赖、接口契约、实现约束、验收标准、规模七个字段齐全；规模约 500 行以内，并且只落在一个构建单元（一个 Cargo crate、`app/` Flutter 工程、`server/`、一个 `tools/<名称>/` 或 `installer/windows/launcher/` C++/CMake 工程）。确需附带少量其他位置的改动（如 `contracts/` 条目、跨语言边界另一侧、归属表的迁移或 CI 配置）时，规模中写明“主包”与“附属”各自的行数。
- b. 依赖闭合：依赖字段与所在文档 §1 依赖图、§3 模块索引一致；CORE 卡只依赖 CORE 卡，平台卡只依赖 CORE 卡或本平台的卡；依赖无环，且依赖卡所在实施阶段不晚于本卡（编号只是标识、不表示先后，见 01 §1）；本卡用到的类型、函数、表与错误码都能在本卡或依赖卡（含间接依赖）的接口契约段找到。
- c. 契约唯一：公共契约只在 01 中定义；02、03 内联的签名与 01 逐字一致。
- d. 契约可编码：函数签名有参数与返回类型；DTO 有字段名、类型、取值范围、是否必填与默认值；错误码有编号、级别、是否可重试与触发条件；表结构有列、类型、约束与索引；文件格式与服务端 API 有版本号、示例与错误响应。
- e. 验收可测：每条验收标准有输入、期望输出或阈值、测量方法，并标注需求编号；性能项引用 CORE-01 全局资源预算表的行名，不另写数字。
- f. 追踪一致：§5“验收所在模块卡”一列与各卡验收标准中的 [Rxx] 双向一致；每条需求至少对应一张卡。
- g. 外部前提：工具链版本、第三方库、账号、证书、供应商与数据许可写在“实现约束”的“外部前提”条目中；未定的引用对应 ADR 或 §6 待确认事项。

#### 8.5.1 整卡语义复核

- 复核人：由修订负责人（lead）指派，不得是该卡最近一次修订的作者；公共契约卡（CORE 卡的接口契约被其他卡引用时）另请一位直接消费方卡的作者确认调用方视角。复核人与日期写入记录。
- 清单：逐项判断 a～g，再判断语义项——S1 目标与范围不超出需求、不漏 [Rxx]；S2 契约中每个类型、函数、op、表、错误码在本卡或依赖闭包内有唯一定义，单位、编码与调用方向一致；S3 每条验收能由本卡代码独立自动化（不能的已标为手动 checklist）并引用 CORE-01 预算行名；S4 规模估算与构建单元可信（不可信先拆卡）；S5 引用的待定 ADR、待确认 Q 已写暂行默认与 Fake 路线；S6 按 §8.1 收集的材料字符数，超过 80000 时是否已按第 6 项裁剪并留记录。
- 记录：附录 D §D.12 每次复核一行（卡、复核人、日期、材料字符数/是否裁剪、a～g 与 S1～S6 结论、发现与处理、结论）；通过后把 §D.10 该卡“当前状态”改为“就绪（D.12 第 n 行）”。
- 流程：作者自查 → 复核人按清单逐项检查 → 有阻断或高问题时结论为“不通过”，作者修订后重新复核 → 通过后更新 §D.10。已就绪卡依赖的契约此后被修改时，引用了被改符号的下游卡回到“待复核”，只需复核受影响的条目。
- S0 路径：S0 的九张卡（CORE-01、CORE-02、CORE-67、CORE-03、CORE-04、CORE-41、CORE-57、AND-01、WIN-01）按 §8.3 的顺序逐张复核；复核未通过的卡不开工，后续卡顺延。
