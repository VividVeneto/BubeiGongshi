**验收标准**
> 阶段划分见来源卡“规模”与“接口契约”末段：阶段1 为本卡 Rust 核心、生成器与消息资源；阶段2 为 Dart 异常桥（`app/lib/binding/errors.dart`，含 `typedef DiagnosticDto = Diagnostic;`），须在 CORE-67 生成 `Diagnostic` 之后、CORE-03 开工前完成（ADR-V5-58 ⑤⑧）。用例编号 **T-01～T-12 稳定**，不复用、不重排，删除只留空号；每项开头标阶段，未标即阶段1。涉及 Dart 侧的断言在 T-01～T-10 中只登记、不执行；T-11、T-12 属阶段2，阶段门槛见 T-12。

- **T-01** [R19] 阶段1｜生成器确定性与结构拒绝：同一 registry 连续两次生成，全部输出物逐字节一致；重复 code、未知 namespace、缺 `message_key`、条目出现未知字段（含把 `condition` 写进 registry）、缺 `surface`、`surface` 取值不在 client/server/both、`surface: client` 却填 `http_status`、`http_status` 非 400–599 整数、`since < 1` 或 `since > registry_version`、`deprecated_since < since` 时生成失败，并指出条目 code。
- **T-02** [R19] 阶段1｜消息资源校验：`fix_hint: true` 但 `errors_zh.arb` 缺 `<message_key>.fix` 键、或 arb 存在基键未登记的孤儿 `.fix` 键时生成失败；`fix_hint: false`（缺省）的条目存在多余 `.fix` 键同样失败。
- **T-03** [R19] 阶段1｜`FmlError` 构造：`FmlError::new(ErrorCode::UnitOverflow)` 的 domain 为 `"unit"`、retryable 与注册表一致、diagnostics 为空、trace_id 为零值；`From<ErrorCode>` 等价于 `new`；`with_diagnostic` 只追加、保序、不改外层 code；`with_trace` 对零值填入、对已有非零值不覆盖；公开 API 清单中没有覆盖 retryable/domain 的构造或方法。领域单测允许零 trace；FFI/HTTP 输出非零由 CORE-03、CORE-22/25 各自的测试执行，本卡不以未交付的边界为前提。
- **T-04** [R19] 阶段1｜规范顺序一致：`FmlError` 字段声明顺序为 `code, domain, retryable, trace_id, diagnostics`（源码扫描 + 注释断言），序列化输出顺序与之一致；`Diagnostic` 输出顺序为 `code, severity, node_path, input_range, args, recovery, needs_confirm`；同一错误的 Rust 序列化结果逐字节等于 `errors-v1` 对应正例的 `canonical`（args 按键排序、缺省可选字段不输出）。
- **T-05** [R19] 阶段1｜`errors-v1` 结构与正例：顶层含 `schema`、`version`、`error_version`、`cases`；每个正例的 `input` 必须是根信封 `{error:{…}}`（缺 `error` 键或用裸 error 对象即失败），Rust 取 `input["error"]` 反序列化后再序列化，与 `canonical` 逐字节相同；正例至少 8 类且各至少一条：真实 32 位小写 trace、多诊断、空诊断数组、省略全部可选字段、args 乱序、`fix_hint: true` 且 `recovery` 等于 `message_key + ".fix"`、`fix_hint: false` 时不输出 `recovery`、severity 为 warning 与 info。`id`（`ERR-nn`）唯一，删例留空号。
- **T-06** [R19] 阶段1｜`errors-v1` 负例：`id`（`ERR-NEG-nn`）、`valid:false`、`why` 齐全；负例至少 9 条且覆盖 `why` 全部 9 种取值（`unknown_field`、`wrong_type`、`range`、`trace_format`、`domain_mismatch`、`retryable_mismatch`、`severity_mismatch`、`recovery_invalid`、`envelope_invalid`）；Rust 侧每条都返回错误且不 panic；`unknown_field` 用例只出现在 error 对象层（诊断对象层未知键不作负例），`envelope_invalid` 指缺 `error` 键或 `error` 非对象。
- **T-07** [R19] 阶段1｜注册表字段校验全集：缺 owner、owner 格式不是 `^(CORE|AND|WIN)-\d{2}$`、首段与 namespace 不符、`message_key` 非派生值、缺简中键、`since`/`deprecated_since` 越界、`http_status` 越界或非整数、`surface: client` 填写 `http_status` 均失败；`surface` 为 server/both 的条目缺省 HTTP 映射 400；废弃条目保留生成与反序列化能力且 code 不复用；缩写与数字段的变体命名（AST 转 Ast、429 保持 429）按规则生成，转换后碰撞拒绝；`as_str`/`domain`/`severity`/`retryable`/`fix_hint`/`is_server_output`/`http_status` 与 registry 全量逐条对照（`http_status` 对 `client` 为 None，对 `server`/`both` 未声明时为 400）；`surface()` 按 `pub fn surface(&self) -> &'static str` 返回注册表原文 `client`/`server`/`both`，并与 `is_server_output()`（`server`/`both` 为 true）逐条同源对照。
- **T-08** [R19] 阶段1｜反序列化与拒绝规则：未知 ErrorCode 的 `FromStr`/`TryFrom`/serde 均返回错误不 panic；Display 与 `std::error::Error` 不含诊断参数或敏感原文；公开字段被改成与注册表不符的 domain/retryable、或 Diagnostic.severity 与自身 code 不符时，Serialize 与 Deserialize 均拒绝；`input_range` 倒序或溢出、error 对象层未知字段或错误类型、trace 大写或非 32 位均拒绝；`recovery` 非派生键、或对应码 `fix_hint` 为 false 时两端按同一规则拒绝。
- **T-09** [R19][R20] 阶段1｜registry 是唯一输入：`contracts/errors/README.md` 由生成器产出，含全部错误码及 owner/severity/retryable/surface/http_status/fix_hint 列；ownership、`shared-writes.json` 的 error 投影、`codes.rs`、`error_codes.g.dart` 与 registry 逐项相同；故意改任一镜像后 `--check` 失败且不写盘，退出码区分 0（无漂移）、1（镜像漂移）、2（registry 或 arb 不可解析、缺 PyYAML）；生成前后非 error 的 shared-writes 项保持不变。
- **T-10** [R19] 阶段1｜REG-01 与全集闭合：registry 交付后 DTOcheck 的 REG-01 三项判定各自可复现失败——(1) `owner` 格式合法但指向不存在或已撤销的卡号；(2) registry 与所有者卡错误表的 owner/severity/retryable/http_status 不一致，纯端侧条目的卡表声明 HTTP 亦失败；(3) 双向全集比对，registry 多余或缺失都失败。全集不硬编码定数，断言“DTOcheck 从 SADD 读到的定义集合与 registry 集合相等”（当前快照 47 张卡、238 条码，仅作基线记录）。registry 未创建时该项输出“未执行”，不得以退出 0 视为通过。同一用例断言 registry 条目不含逐 op 错误集合字段、`manifest.json` 的 `error_codes` 由 CORE-100 与 DTO-06/DTO-18 校验（ADR-V5-58 ⑥），且 DTO-06 双向比对的对照源是 op 所有者卡的逐 op 错误镜像——卡行或 `error_codes` 任一侧缺码均失败（ADR-V5-55），并断言因增码而递增 `registry_version` 时 `error_version` 保持不变（ADR-V5-58 ⑦）。
- **T-11** [R19] 阶段2｜Dart 异常桥：`FmlException('SYNC_NOT_AVAILABLE')` 的 retryable 等于生成表值、traceId 为非零 32 位小写十六进制且两次构造不同；命名构造器的非法参数（未登记 code、traceId 大写或全零、diagnostics 元素类型不符）抛 `ArgumentError`；`fromJson` 的载荷问题（缺字段、类型不符、domain/retryable/severity 与生成表不符、error 对象层未知字段、零值 trace、`recovery` 非派生键、缺 `error` 键）抛 `FormatException`，两类异常不混用，且异常消息不含原始载荷；构造器与工厂均无 retryable/domain 参数（源码扫描）；`Diagnostic` 内部未声明键被忽略且不因此失败。
- **T-12** [R19] 阶段2｜阶段门槛与别名：`app/lib/binding/errors.dart` 中 `DiagnosticDto` 必须是 CORE-67 生成类的别名（`typedef DiagnosticDto = Diagnostic;`，源码扫描），该生成类来自 `app/lib/binding/dto/types.g.dart`；阶段2 未交付时，交付记录与复核只写“阶段1 通过、阶段2 未执行”；在 CORE-67 生成 `Diagnostic` 之前以手写类代替生成类、或据此宣称整卡通过，均判本卡验收失败；CORE-67 若改变生成类名，本卡按 README §8.4 走变更单，不改别名以外的内容。
